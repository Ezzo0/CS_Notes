# Explanation
- The Internet design paradigms are just one of many possible designs, and many design choices were made years ago, before the Internet grew to its current scale. Other designs exist, and debates still exist about what the best design is.
- For example, the Internet was built to be federated (independent operators cooperating), but in recent years, software-defined networking (SDN) emerged as a more centralized approach to managing a network.
- In the original Internet, switches were intentionally designed to be dumb and forward data without parsing it. However, in the modern Internet, attackers might try to overwhelm a switch by flooding it with useless data, and switches might need a way to detect this. Early Internet designers who came up with the dumb infrastructure paradigm did not consider this security implication.
#### Narrow Waist
- It’s possible to have multiple protocols at a given layer. For example, at [[0x00_Layers of the internet#Layer 7 Application|Layer 7]], we could use HTTP to serve websites, or NTP to sync system clocks, both built on the same Internet infrastructure. Or, at [[0x00_Layers of the internet#Layer 2 Link Layer|Layer 2]], we could use Ethernet for wired networks, or Wi-Fi for wireless networks.
- Note that even though there are multiple protocols at a given layer, you can commit to using a specific stack of protocols for your application. For example, you can commit to using HTTP over TCP over IP, and you don’t need to use the other [[0x00_Layers of the internet#Layer 7 Application|Layer 7]] or [[0x00_Layers of the internet#Layer 4 Transport|Layer 4]] protocols. Then, everybody using your application uses the same stack.
	![networkLayersProtocols](https://textbook.cs168.io/assets/intro/1-31-multi-protocols.png)
- If you look at this diagram, you’ll notice there’s only one protocol at [[0x00_Layers of the internet#Layer 3 Internet Layer|Layer 3]]. This is the “narrow waist” that enables Internet connectivity. Ultimately, everybody on the Internet must agree to speak IP so that packets can be sent across the Internet.
#### Demultiplexing
- When we're looking at this diagram, remember that when you receive a packet, it has all of its headers wrapped around it. As the packet is passed up to higher layers, each layer unwraps its corresponding header.
- The packet starts as a bunch of ones and zeros on the wire. Then, as it moves up the stack, [[0x00_Layers of the internet#Layer 2 Link Layer|Layer 2]] unwraps its header and passes the packet to [[0x00_Layers of the internet#Layer 3 Internet Layer|Layer 3]], which unwraps another header, and so on until we reach the top.
- However, when we look at this narrow-waist architecture, there is a problem once we reach the higher layers. Let's say we're at [[0x00_Layers of the internet#Layer 3 Internet Layer|Layer 3]] and have just unwrapped the packet.
- There are now different protocols, such as TCP and UDP. You can think of these as different programs running on your computer. Which one should process this packet? Is it a TCP packet, meaning the TCP code should process it, or is it a UDP packet, meaning the UDP code should process it?
- Similarly, once the packet reaches TCP and TCP unwraps its [[0x00_Layers of the internet#Layer 4 Transport|Layer 4]] header, how does TCP know whether it should pass the packet to the HTTP code, the SMTP code, or some other piece of code?
- As we work our way up the stack, there are points where we need to know which path to take. We therefore need something to tell the IP or TCP protocol which way to send the packet as it moves further up the stack and which protocol should handle it next.
	![demultiplexing](https://textbook.cs168.io/assets/intro/1-32-demultiplex.png)
- This problem is called **demultiplexing**. We have multiple choices, and we need to narrow them down to the correct one.
- The way we solve this is by using information in the [[0x01_Headers|headers]]. Headers already contain useful information about a packet, and we can add another piece of information indicating which protocol should receive the packet next.
- For example, at Layer 3, IP can have a header field indicating that the packet contains a TCP segment. When the IP header is unwrapped, the information inside should be passed to the TCP code for processing. Alternatively, the header might indicate that the packet contains a UDP datagram. In that case, the packet should be passed to the UDP protocol.
	![layer3Demultiplixing|400](https://textbook.cs168.io/assets/intro/1-33-layer3-demultiplex.png)
- The same basic idea applies at Layer 4. Once a packet reaches TCP, we still need to determine which application should receive it. For example, my computer might currently be running Firefox to display the slides, Zoom to record the lecture, an email client, Slack, and many other applications.
- When TCP receives a packet, it needs to know which application the packet is intended for. Is it for Firefox, the email client, Slack, or something else?
- To solve this, we assign each application a **port number**. For example, Firefox might use port 40,000, an email client might use port 50,000, and Slack might use port 60,000.
- The TCP header contains a field specifying the destination port. When TCP receives a packet destined for port 40,000, it knows that the packet should be passed to Firefox. If the destination port is 60,000, TCP knows that the packet should be passed to Slack.
	![programPort|400](https://textbook.cs168.io/assets/intro/1-34-layer4-demultiplex.png)
- In networking, two different things are called ports. A physical port is the actual physical place where you plug a link into a switch. A logical port is a number in the Layer 4 header to disambiguate which application a packet belongs to.
	![ports](https://textbook.cs168.io/assets/intro/1-37-logical-physical-port.png)
- If you open up your computer and think about where the TCP protocol is running or where an application like Firefox is running, you would get roughly the following picture.

- At the very lowest level, we have the **Network Interface Card (NIC)**. This is an actual computer chip—a physical piece of hardware responsible for sending and receiving packets.
	![layersBetweenSoftandHardware](https://textbook.cs168.io/assets/intro/1-38-layers-in-os1.png)
- It takes the ones and zeros that make up the data and broadcasts them as radio waves or sends them across a physical wire. [[0x00_Layers of the internet#Layer 1 Physical Layer|Layers 1]] and [[0x00_Layers of the internet#Layer 2 Link Layer|2]], which deal with packets and sending ones and zeros across the network, are implemented in hardware on the network interface card.
- Moving up the stack, **[[0x00_Layers of the internet#Layer 3 Internet Layer|Layers 3]] and [[0x00_Layers of the internet#Layer 4 Transport|4]] are implemented in software**. These are actual pieces of code rather than dedicated hardware chips. You can even think of your operating system as containing the implementation of protocols such as TCP. For example, if you're running Windows, the Windows operating system contains an implementation of TCP.
- Finally, the actual **applications** run at the [[0x02_Limited Direct Execution#Problem 1 Restricted Operations|user level]]. For example, if I open a text editor and run a Python program, that program is running in user space rather than directly at the operating-system level. Applications such as Firefox, Zoom, email clients, and other programs run at this level.
- Another way to understand this architecture is by looking at what each level thinks about. At the very bottom, the hardware thinks in terms of **individual packets**. It essentially sees a blob of data and sends it across the wire.
- When it receives a bunch of ones and zeros, it treats them as another blob of data. The hardware doesn't think about connections. Instead, it thinks about individual packets independently, without necessarily considering the relationship between them.
- At the very top, applications think in terms of **connections**. For example, when you open your web browser, the browser can think of itself as having a connection to YouTube, with YouTube and the browser exchanging lots of data so that you can download a video.
- Therefore, at [[0x00_Layers of the internet#Layer 7 Application|Layer 7]], it makes sense to think about long-term connections, while down in the hardware it makes sense to think about individual packets traveling across the network.
- The operating system, particularly Layers 3 and 4, can be viewed as **bridging these two abstractions**. It takes individual packets and works with them to create and manage longer-term communication and connections.
#### End-to-End Principle
- Why did we design the Internet with the layering structure that we did? Why do only the hosts understand Layers 4 and 7, and not the routers as well? Should we implement reliability (Layer 4) in the network, or only at the end hosts?
- For now, let’s think of a simple protocol for reliability. Host A wants to send 10 packets to Host B, so it sends the packets, numbered 1 through 10, across the network. The goal is for B to either receive all the packets, or realize that some packets got lost and error (we’ll ignore recovering from the error).
- What would the Internet look like if we implemented reliability in the network? Unlike our picture from earlier, every router must now understand Layer 4 in addition to Layers 1, 2, and 3.
- With this new picture, an intermediate router must reliably send a packet to its next hop. It must guarantee that the next hop received all the packets, and if not, the router must re-send any lost packets. The hosts don’t check that all packets were received, and instead rely on the network to ensure that all packets were received.
	![reliabilityInNetwork](https://textbook.cs168.io/assets/intro/1-41-reliability-in-network.png)
- In this approach, the hosts have to trust the network. If one of the routers is buggy, and drops a packet, there’s nothing the hosts can really do about it.
	![buggyRouter](https://textbook.cs168.io/assets/intro/1-42-buggy-reliability-in-network.png)
- The other approach is the end-to-end approach, where we do not implement reliability in the network, and we instead force the two end hosts to enforce reliability. Routers can drop packets, and it’s up to the end hosts to verify that all packets were received.
	![reliabilityInHost](https://textbook.cs168.io/assets/intro/1-43-reliability-in-endhost.png)
- In the end-to-end approach, where the end hosts implemented reliability, the control is with the hosts. The hosts could still be buggy and drop packets, but this time, the hosts have the power to fix the bug themselves.
- More generally, if you’re writing code, it’s better if you have the control over making the feature correct, instead of relying on other people who might mess up (and you can’t fix their mistakes).
- With this comparison in mind, if we used the first approach, where we relied on the network to be correct, we can’t actually guarantee perfect reliability if the network is buggy. The end hosts would probably end up doing an end-to-end check (as in the second solution) anyway.
- In the old Internet, every link did implement reliability. However, as we saw, the modern Internet only implements best-effort in the network, and forces the end hosts to implement reliability, in line with the end-to-end principle.
- Some application requirements must be implemented end-to-end in order to ensure correctness. Also, the end-to-end implementation is sufficient, and no additional support from the network is needed. Because the end-to-end implementation alone is sufficient, adding network functionality would introduce additional unnecessary complexity (and cost), without helping us actually achieve the requirements.
- Note that the end-to-end principle is not a proof or a theorem that’s always true. It’s a guiding principle and a philosophical argument, and different designers might make different arguments for or against the principle.
- Here’s an example of the end-to-end principle not being a strict rule. Even though the end-to-end principle says to implement reliability in the end hosts only, we could still add some extra reliability in the network in addition to the end-to-end check.
- This might be useful if we have highly unreliable links. Suppose there are 10 links between A and B, and each one fails 10% of the time. Then, each time we send the packet, it has a 65% chance of getting dropped.
- However, if each router was modified to send two copies of the packet for reliability purposes, each link only fails 0.1% of the time, and packets now only have a 1% chance of getting dropped. Wireless links will sometimes implement reliability to reduce error rates and improve performance for the end hosts.
- The end-to-end principle extends to other fields as well. For example, in security, the end-to-end principle might say that two end hosts communicating should encrypt their messages at the end hosts, instead of at intermediate points in the network.
